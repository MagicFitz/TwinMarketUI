# Tushare 金融数据接入与当前市场快照设计

本文给出 TwinMarket 接入 Tushare Pro 的建议方案，目标是让系统可以用近期 A 股行情、交易日历、估值、资金流和新闻构建可复现的市场环境，并把数据源配置、同步过程、质量状态和环境快照嵌入现有前后端。

本文基于 2026-10-06 的代码工作树。当前 `data/stock_data.csv` 的行情范围为 2023-01-03 至 2025-01-10，`data/trading_days.csv` 截至 2025-01-10，`data/sorted_impact_news.pkl` 的新闻范围为 2023-06-15 至 2024-12-15，因此现有数据不能代表当前市场。

## 1. 结论

推荐采用“数据源连接 → 异步同步任务 → 标准化与质量校验 → 发布不可变市场快照 → Run 固定引用快照”的数据链路。

而不是让模拟进程直接调用 Tushare，也不要直接覆盖当前 `data/` 下的生产文件。

首期应以**收盘后日级快照**为目标，而不是盘中实时撮合：TwinMarket 当前是自然日主循环和日级撮合，Tushare A 股日线通常在收盘后入库，申万行业日线在交易日 18:30 更新。把盘中数据直接喂给现有日级模型既不能忠实模拟盘口，也会造成同一个 Run 在不同时间启动得到不同输入。实时行情可在后续作为 Market 页面上的只读“当前市场预览”，但不能默认成为仿真输入。

首期应保留现有 10 个自定义行业指数及其代码，不把它们静默替换为申万指数。系统里的 `TLEI`、`FSEI` 等资产由 50 只成分股和固定权重定义，而 Tushare 返回标准 A 股或标准指数代码。需要先拉取成分股数据，再由一个明确版本的聚合规则生成 10 个兼容现有模型的行业指数。

## 2. 当前架构与主要缺口

### 2.1 现有边界

当前关键链路是：

```text
Studio / React 前端
    │ REST / SSE
    ▼
FastAPI（backend/app/main.py）
    │ Registry、Worker、运行目录
    ▼
backend.worker → simulation.py
    │
    ├─ data/trading_days.csv
    ├─ data/sorted_impact_news.pkl
    ├─ data/stock_data.csv
    └─ 由 data/sys_1000.db 复制出的 Run 私有数据库
```

按照仓库当前约定，本方案以 `studio/` 作为首要前端落点：Setting 管理连接凭据，Market 管理数据同步和环境快照。（顶层 `frontend/` 已于 2026-11-03 删除，不再需要同步 API 类型。）

### 2.2 必须解决的代码问题

1. `simulation.py` 从 `TWINMARKET_DATA_DIR` 读取新闻和交易日历，但 `trader/matching_engine.py` 的真实行情路径仍默认写死为 `data/stock_data.csv`。如果不先统一路径，选择新快照后撮合仍可能混用旧行情。
2. `simulation.py` 当前用 `pretrade_date` 判断当天是否开市；正确逻辑应读取 `cal_date` 且 `is_open == 1/open`。兼容导出器可以继续生成三列 CSV，但仿真端必须修正判断。
3. Run 创建时只记录全局行情文件指纹，没有稳定的 `market_snapshot_id`。如果全局文件随后被更新，历史 Run 无法准确复现。
4. `prepare_simulation_run.py` 只裁剪用户，不会把指定快照中的最新 `StockData` 注入 Run 数据库。仅更新 CSV 不足以让 Agent 看到近期历史行情。
5. 新闻代码对每日数据执行 `.iloc[0]`，日期缺行会直接失败。快照必须为范围内每个自然日提供一行，缺少新闻时使用空列表并标记质量降级。
6. 当前 Market 数据工作台和 Setting 金融数据源入口是规划按钮，后端也只有模型设置服务，没有金融数据源、同步任务或快照 API。

## 3. 目标架构

```text
Setting：保存/测试 Tushare 连接
                │
                ▼
POST /api/market/sync-jobs
                │
                ▼
独立 market_worker 子进程
    ├─ TushareProvider：限流、重试、权限探测
    ├─ Raw landing：保存原始响应和请求清单
    ├─ Normalizer：统一代码、日期、单位和字段
    ├─ CustomIndexBuilder：50 只成分股 → 10 个 TwinMarket 指数
    ├─ NewsBuilder：去重、归日、相关性排序
    └─ Validator：完整性、连续性、覆盖率和异常值
                │
                ▼
不可变 market snapshot（先临时目录，校验通过后原子发布）
                │
                ├─ Market 页面预览、质量报告、发布/回退
                └─ 创建 Run 时固定 snapshot_id 与文件指纹
```

模拟进程只读本地已发布快照，不持有 Tushare Token，不访问网络。这样能隔离外部接口波动、控制成本，并保证实验可复现。

## 4. Tushare 数据集选择

### 4.1 首期最小数据集

| TwinMarket 需求 | Tushare 接口 | 用途 | 首期策略 |
| --- | --- | --- | --- |
| 开市/休市与前一交易日 | `trade_cal` | 生成交易日历 | 必选 |
| 50 只成分股日行情 | `daily` | 收盘价、前收、涨跌、成交量、成交额 | 必选 |
| 估值和股息率 | `daily_basic` | `pe_ttm`、`pb`、`ps_ttm`、`dv_ttm` | 推荐；无权限时允许降级 |
| 大单资金流 | `moneyflow` | 合成 `elg_amount_net` | 可选；无权限时置空而不是伪造 0 |
| 新闻快讯或长文 | `news` / `major_news` | 当日 Agent 信息环境 | 可选且需要单独权限 |
| 申万行业日线 | `sw_daily` | 标准行业基准、交叉校验 | 第二阶段；不是自定义指数的直接替代 |
| 申万实时行情 | `rt_sw_k` | Market 只读实时预览 | 第三阶段；不得默认进入日级快照 |
| A 股实时分钟 | `rt_min` | 未来盘中模型 | 暂不接入现有日级撮合 |

Tushare 各接口权限、积分和更新时间不同，不应在代码里假定账户一定拥有某个接口。保存数据源后执行轻量权限探测，并在 UI 中分别展示“可用”“无权限”“限流”“尚未测试”。`news` 与 `major_news` 是单独权限；`trade_cal`、`moneyflow`、`sw_daily` 等也有各自积分要求。

### 4.2 为什么首期拉成分股而不是直接使用申万指数

现有 `StockProfile` 和 Prompt 把 10 个资产描述成明确的自定义篮子，例如 TLEI 由中远海控和中国船舶组成。直接把 TLEI 映射到一个标准申万交通运输指数会改变资产语义、成分和历史收益分布，也会让旧实验与新实验失去可比性。

建议把成分、权重和生效时间移出 `trader/utility.py` 的自然语言常量，放到可校验的 `data/market_assets.yaml`：

```yaml
schema_version: 1
assets:
  TLEI:
    name: 交通与运输指数
    base_currency: CNY
    constituents:
      - ts_code: 601919.SH
        weight: 0.5234
      - ts_code: 600150.SH
        weight: 0.4766
```

该文件需要版本号、权重合计校验和生效日期；快照元数据记录其 SHA-256。未来允许发布新资产包版本，但已创建 Run 继续引用原版本。

## 5. 自定义行业指数的转换规则

### 5.1 行情

对每个自定义指数，使用成分股固定权重和当日收益率进行链式计算：

```text
index_return(t) = Σ weight(i) × stock_return(i, t)
close(t)        = close(t-1) × (1 + index_return(t))
pre_close(t)    = close(t-1)
change(t)       = close(t) - pre_close(t)
pct_chg(t)      = index_return(t) × 100
```

首个新增日期使用旧数据最后一个收盘点位作为桥接基准，避免 2025-01-10 之后出现人为跳点。停牌成分股当日收益按 0 处理，但需要记录参与权重覆盖率；覆盖率低于 80% 时快照不得自动发布。

成交量使用成分股成交量之和，成交额使用成分股成交额之和。必须在 Normalizer 中显式统一 Tushare 的“手/股”和“千元/万元/元”单位，不能仅靠列名推测。所有输出字段在快照元数据中记录单位。

### 5.2 估值与资金流

- 正 PE、PB、PS 使用组合倒数加权：`1 / Σ(weight / ratio)`；非正或缺失值不参与，并记录有效权重。覆盖不足时写 `null`。
- `dv_ttm` 使用有效成分的权重加总。
- `elg_amount_net` 使用各成分 `buy_elg_amount - sell_elg_amount` 后求和，并统一为万元；没有 `moneyflow` 权限时写 `null`，不可写 0，因为 0 表示“确认没有净流入”。
- `ma_hfq_5/10/30`、`vol_5/10/30` 从合成后的指数序列重算，不把单股均线再次加权。

### 5.3 新闻

Tushare 新闻接口不直接提供 TwinMarket 现有的“影响力排序”结果。首期应采用可解释、确定性的兼容转换：

1. 按 URL/标题/正文哈希去重；
2. 以 Asia/Shanghai 时区归入自然日；
3. 对 50 只成分股名称、代码、10 个行业名称和全市场关键词做相关性计分；
4. 同分时按发布时间倒序，每日最多保留可配置数量；
5. 为同步范围内每个自然日输出一行 `{"cal_date": ..., "news": [...]}`；
6. 在元数据记录 `ranking_method` 和版本，不把“相关性排序”冒充为模型推断的影响力。

后续可以增加 LLM 分类和情绪/影响评分，但它们应作为派生字段，并记录模型与 Prompt 版本。新闻更新后需要重建 `InformationDB_news_2023` 的替代索引；建议将目录改名为与快照绑定的 `news_index/`，避免年份写死。

## 6. 本地存储与快照格式

建议新增：

```text
backend/data/market.sqlite3             # 数据源、任务、快照注册表
data/market_assets.yaml                 # 自定义资产及成分版本
data/market_staging/<job_id>/           # 未发布临时数据
data/market_snapshots/<snapshot_id>/
├─ snapshot.json                        # 来源、范围、版本、质量和文件指纹
├─ raw/
│  ├─ request_manifest.jsonl
│  └─ tushare/*.jsonl.gz                # 原始响应，便于审计和重放
├─ normalized/
│  ├─ constituents.parquet
│  ├─ custom_indices.parquet
│  ├─ calendar.parquet
│  └─ news.parquet
├─ stock_data.csv                       # 现有撮合兼容格式
├─ trading_days.csv                     # 现有仿真兼容格式
├─ sorted_impact_news.pkl                # 过渡期兼容格式
└─ news_index/                           # 与快照一致的 FAISS 索引
```

如果不希望首期引入 Parquet 依赖，`normalized/` 可以先用压缩 JSONL；但是兼容输出仍应由标准化层生成，不能直接把 Tushare DataFrame 重命名后写入。

`snapshot.json` 至少包含：

```json
{
  "schema_version": 1,
  "snapshot_id": "market-20261006-close-v1",
  "provider": "tushare",
  "as_of": "2026-10-06T18:45:00+08:00",
  "effective_through": "2026-10-06",
  "status": "ready",
  "datasets": {},
  "asset_definition_sha256": "...",
  "transform_version": "twin-index-v1",
  "quality": {"errors": [], "warnings": []},
  "files": {"stock_data.csv": {"sha256": "...", "bytes": 0}}
}
```

快照目录一经发布只读。同步任务先写 staging，完成校验后使用同文件系统原子重命名发布；失败任务保留错误摘要，定期清理 staging，但绝不能修改旧快照。

## 7. 后端设计

### 7.1 模块建议

```text
backend/market_data/
├─ providers/base.py          # Provider 协议与统一异常
├─ providers/tushare.py       # HTTP 客户端、分页、限流、重试、权限错误
├─ assets.py                  # 资产定义读取和校验
├─ normalize.py               # 字段、代码、日期、时区和单位标准化
├─ indices.py                 # 10 个自定义指数聚合
├─ news.py                    # 新闻去重、归日和兼容导出
├─ quality.py                 # 数据质量规则
├─ snapshots.py               # staging、发布、指纹、回退
└─ registry.py                # source/job/snapshot 元数据

backend/services/data_sources.py
backend/services/market_sync.py
backend/market_worker.py
script/sync_market_data.py    # 与 Web 使用同一 service 的 CLI
```

仓库已有 `requests`，首期可直接实现 Tushare HTTP POST 协议，减少 SDK 版本耦合；Provider 对上层暴露稳定方法，测试中注入假响应。如果团队更偏好官方 Python SDK，也必须把 SDK 封装在 Provider 内，不能让 DataFrame 形状扩散到领域层。

同步不能在 FastAPI 请求线程内执行。参考现有 Run Worker，`POST /sync-jobs` 只创建任务并启动独立 `backend.market_worker`；前端轮询任务状态即可，后续再考虑 SSE。相同数据源和重叠日期范围同时只允许一个写任务。

### 7.2 Registry 表

建议至少包含：

| 表 | 关键字段 |
| --- | --- |
| `data_sources` | `source_id`、`provider`、`enabled`、`credential_ref`、`last_tested_at`、`capabilities_json` |
| `sync_jobs` | `job_id`、`source_id`、`requested_range`、`datasets_json`、`status`、`progress`、`error_code`、时间戳 |
| `market_snapshots` | `snapshot_id`、`status`、`as_of`、`effective_through`、`path`、`quality_json`、`created_by_job_id` |

凭据正文不进入 SQLite、任务参数、日志或 Run manifest。`credential_ref` 只指向环境变量或权限为 `0600` 的本地配置项。

### 7.3 API 草案

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/settings/data-sources` | 返回脱敏后的金融数据源和能力状态 |
| `PUT /api/settings/data-sources/tushare` | 保存/更新 Token；省略 Token 表示保留，空串表示清除 |
| `POST /api/settings/data-sources/tushare/test` | 轻量调用并探测各能力，不下载大批量数据 |
| `GET /api/market/overview` | 当前已发布快照、覆盖日期、质量和任务摘要 |
| `POST /api/market/sync-jobs` | 创建回补或增量同步任务 |
| `GET /api/market/sync-jobs/{job_id}` | 获取阶段、进度、限流等待和错误摘要 |
| `POST /api/market/sync-jobs/{job_id}/cancel` | 请求安全取消；已发布快照不受影响 |
| `GET /api/market/snapshots` | 列出不可变快照 |
| `GET /api/market/snapshots/{snapshot_id}` | 返回覆盖率、文件指纹和校验报告 |
| `POST /api/market/snapshots/{snapshot_id}/activate` | 切换新建 Run 的默认快照，不改变既有 Run |

所有响应都使用稳定错误码，例如 `TUSHARE_AUTH_FAILED`、`TUSHARE_PERMISSION_DENIED`、`TUSHARE_RATE_LIMITED`、`DATA_COVERAGE_INCOMPLETE`、`SNAPSHOT_VALIDATION_FAILED`，前端不要解析供应商原始中文错误文本。

### 7.4 限流、重试与幂等

- 按“交易日 + 接口”拉取全量截面，避免为每只股票循环调用；`daily` 官方也建议按交易日拉全市场。
- 只保存当前 50 只成分股，但原始请求清单必须记录接口、参数、字段、返回行数和响应哈希。
- 对网络超时、5xx 和明确的限流错误做带抖动的指数退避；鉴权和无权限错误立即失败，不盲目重试。
- `(provider, api_name, parameters_hash, response_hash)` 用于重复请求识别；规范化表按自然键 upsert。
- 增量同步从最新已发布交易日的下一天开始，并额外重拉最近 3 个交易日以吸收供应商修订；发布新快照而不是原地修改旧快照。
- 请求和日志中始终脱敏 Token；异常对象进入日志前也要清洗。

## 8. Run 与仿真内核的接入

### 8.1 Run 配置

在 `RunConfig` 增加：

```json
{
  "market_snapshot_id": "market-20261006-close-v1",
  "market_data_mode": "snapshot",
  "allow_missing_news": true
}
```

创建 Run 时：

1. 校验快照为 `ready`，且覆盖 `start_date` 至 `end_date`；
2. 将 `snapshot_id`、`effective_through`、转换版本、资产定义哈希和所有兼容文件指纹写入 `manifest.json`；
3. Run 离开 draft 后不允许修改快照；“复制 Run”可以选择沿用旧快照或显式升级到新快照；
4. 开始日期不得晚于快照的 `effective_through`，也不得让 Agent 读取模拟日之后的数据。

### 8.2 Worker 和数据路径

Worker 为每个 Run 设置：

```text
TWINMARKET_DATA_DIR=<snapshot_directory>
TWINMARKET_MARKET_SNAPSHOT_ID=<snapshot_id>
```

同时修改 `test_matching_system` / `update_stock_data_table` 调用链，让 `real_data_path` 显式来自该目录，彻底删除撮合核心对仓库根 `data/stock_data.csv` 的隐式依赖。

### 8.3 Run 数据库准备

推荐在 `prepare_simulation_run.py` 增加 `--market-snapshot`：复制基础用户数据库并裁剪用户后，在同一事务里用快照行情构建 Run 私有 `StockData`。不要修改 `data/sys_1000.db`。

构建时只注入 Run 开始日前可见的历史窗口，例如至少 30 个交易日，以支持 MA30；模拟日当天的真实收盘数据只能作为撮合后的校准基准，不能提前进入 Agent 的观察查询。应增加自动化测试验证 `Agent observation date <= simulation_date - 1 trading day`。

### 8.4 新闻降级

如果账户没有新闻权限：

- 快照仍可发布为 `ready_with_warnings`，前提是用户明确允许无新闻模式；
- 每个自然日输出空新闻列表，避免仿真崩溃；
- New Run 页面显示“行情已更新，新闻缺失”，而不是笼统显示“市场数据可用”；
- Run manifest 记录新闻能力为 `missing`，结果页保留该研究限制。

## 9. 前端嵌入方案

### 9.1 Setting → 金融数据源

把现有“暂无连接 / 添加数据源”替换为 Tushare 连接卡片：

- 状态：未配置、未测试、可用、部分权限、失败；
- Token 密码框只支持新增/替换，不回显原值；
- 固定服务地址，不允许用户输入任意 URL，避免 SSRF；
- “测试连接”结果按能力展示：日线、交易日历、估值、资金流、新闻、申万行业、实时行情；
- 显示最近测试时间和供应商错误的可理解摘要；
- 设置页只管理访问连接，不在这里启动同步。

### 9.2 Market → 数据工作台

把“更新数据”升级为实际工作流：

1. 顶部状态卡：当前默认快照、有效截至日期、行情/日历/新闻覆盖、质量状态；
2. 同步抽屉：增量更新或指定日期回补、数据集选择、预计调用范围、无新闻是否允许；
3. 任务列表：排队、拉取、标准化、聚合、校验、建索引、发布等阶段与可重试错误；
4. 质量面板：缺失交易日、成分覆盖率、异常涨跌、重复行、字段空值、新闻缺口；
5. 快照列表：默认标记、范围、来源、转换版本、创建时间；只允许切换默认，不允许修改历史快照；
6. 资产映射页：展示 TLEI 等自定义指数的成分和权重，让数据语义对研究者可见。

同步完成不等于自动切换默认快照。建议首期在校验通过后由用户点击“设为新实验默认”，避免一次错误同步立刻影响后续实验。

### 9.3 Experiment → 新建 Run

新增“市场环境快照”选择器，默认选中当前激活快照，并显示：

- 数据有效截至日期；
- 行情、估值、资金流、新闻的可用状态；
- 是否覆盖所选模拟日期；
- 资产定义版本和警告。

如果日期超出快照范围，禁用启动并给出“前往 Market 更新数据”的可执行入口。Run 详情和结果页始终显示实际使用的快照，而不是当前全局默认值。

### 9.4 实时预览的后续边界

第三阶段可以在 Market 页增加“盘中观察”卡片，通过 `rt_sw_k` 或 `rt_min` 显示带时间戳的延迟行情。该数据只进入短 TTL 缓存，不写入已发布日级快照，不影响运行中的实验，并明确标注“预览，不是本次模拟输入”。

## 10. 数据质量与发布门槛

快照发布前至少检查：

- 日期范围内交易日历无缺口、日期唯一且单调；
- 每个开市日 10 个自定义指数都有一行数据；
- 每个指数的有效成分权重不低于 80%，低于 95% 产生警告；
- `close > 0`，`pre_close > 0`，`pct_chg` 与价格变化在容差内一致；
- 主键 `(ts_code, date)` 唯一；
- MA5/10/30 只使用截至当日的数据；
- 兼容 CSV 的列、类型和单位满足现有 SQLite 写入要求；
- 日历中的最后开市日不晚于行情有效日期；
- 新闻每日有容器行，新闻条目去重且时间不越过快照 `as_of`；
- FAISS 元数据数量与索引向量数量一致；
- 所有发布文件的 SHA-256 与 `snapshot.json` 一致。

另外执行一条最小烟雾 Run：1 个用户、2 个交易日、假模型响应，验证准备、感知、撮合、结算和结果查询全链路。这比只检查文件存在更能发现列名、日期和路径兼容问题。

## 11. 安全、许可与运维

- Token 优先由 `TUSHARE_TOKEN` 环境变量提供；本地桌面场景允许写入 `config/data_sources.yaml`，文件权限为 `0600`，API 永不回显原文。
- Tushare 请求固定发送到官方 API 地址；不接受用户可编辑的 base URL。
- Token 不写入 Git、运行清单、事件、日志、原始请求清单或错误响应。
- 原始新闻内容和行情数据的保存、共享与发布应遵守 Tushare 账户授权和数据许可；系统默认只做本地研究使用。
- 每日自动同步建议安排在交易日 18:45（Asia/Shanghai）之后，以覆盖申万日线更新时间；首期先交付手动同步和 CLI，稳定后再接系统调度器。
- 自动任务失败时继续保留并使用上一个已发布快照，不能留下半写入的“最新数据”。
- 监控指标至少包括：任务成功率、接口延迟、限流次数、最新有效交易日、数据缺口数、快照发布时间和原始/规范化行数。

## 12. 分阶段实施

### 阶段 0：先修复数据边界

1. 统一所有行情读取到 `TWINMARKET_DATA_DIR`；
2. 修正交易日判断；
3. 给 Run 增加 `market_snapshot_id` 和 manifest 指纹；
4. 让数据库准备脚本从快照注入 `StockData`；
5. 为无新闻日期增加空列表兼容。

这是接入 Tushare 前的必要工作，否则会出现新旧数据混用。

### 阶段 1：日级行情 MVP

1. 实现脱敏 Tushare 设置和连接测试；
2. 接入 `trade_cal`、`daily`、可选 `daily_basic`；
3. 实现 50 只成分股到 10 个自定义指数的聚合；
4. 实现 staging、质量校验、不可变快照和手动激活；
5. 完成 Setting、Market、New Run 三处 UI；
6. 用假 Tushare 服务完成端到端测试。

完成标准：能从旧数据截止日增量更新到最近已收盘交易日，并用新快照成功跑完最小实验；旧 Run 的输入和结果不变。

### 阶段 2：资金流与新闻

1. 能力探测后接入 `moneyflow`；
2. 接入有权限的新闻源，完成去重、相关性排序和每日兼容导出；
3. 为每个快照重建新闻向量索引；
4. 在 Run 和结果页显示数据能力与缺失警告。

### 阶段 3：标准行业基准和实时预览

1. 接入 `sw_daily` 作为基准序列，比较自定义指数与标准行业表现；
2. 可选接入 `rt_sw_k` / `rt_min` 作为只读盘中预览；
3. 如果未来真正需要盘中仿真，应另建分钟级事件时钟、订单簿和成交模型，不能只替换现有 CSV。

## 13. 测试清单

### 单元测试

- Tushare 成功、空结果、2002 权限错误、限流、超时和畸形响应；
- Token 脱敏与更新/保留/清除语义；
- 日期、代码和单位转换；
- 指数链式计算、停牌、缺失值、负 PE 和权重覆盖；
- 日历兼容导出及开市判断；
- 新闻去重、时区归日、空日补齐；
- 快照指纹、原子发布、幂等和取消。

### 集成测试

- 使用固定假响应完成 `sync job → snapshot → activate`；
- 后端重启后任务和快照元数据仍可读取；
- 同范围重复同步不破坏旧快照；
- 创建 Run 后修改默认快照不影响该 Run；
- Run 数据库中的 Agent 只能看到模拟日之前的数据；
- 没有新闻权限时，在明确允许降级后仍可完成实验。

### 前端测试

- Token 永不回显；
- 部分权限和失败原因可区分；
- 同步中刷新页面可以恢复任务状态；
- 数据覆盖不足时不能启动 Run；
- 移动端保持底部主空间导航，任务详情使用抽屉而不是挤压主表格。

## 14. 建议的首个开发切片

第一个可合并切片应保持小而完整：

1. 新增 Tushare 脱敏设置和 `trade_cal`/`daily` 连接测试；
2. 用固定的两天假数据生成一个本地快照；
3. 修复数据路径与交易日判断；
4. 让一个最小 Run 明确引用该快照并跑通；
5. Market 页面只展示这个快照的范围、质量和文件指纹。

不要在第一个切片同时实现新闻、实时行情、自动调度和资产包编辑。先证明“快照输入可以无混用地进入 Run，且历史 Run 可复现”，再扩充外部数据能力。
